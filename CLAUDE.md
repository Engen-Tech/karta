## Standing directions (Claude sessions in this repo)

- **Nothing reaches the default branch by a direct commit, except a fully committed binder.** Doing karta work here, main is reached through a branch and a merge — the binder commit (its JSON plus the roundtable record filed with it) is the one exception, because a binder is a plan of record rather than a change to the framework. Code, hooks, scripts and prose all go on a branch first. A karta delivery uses its own `karta/<slug>/integration` branch and is landed by the human; ordinary work uses a plainly-named branch merged `--no-ff`, and should NOT borrow the `karta/*/integration` namespace, which means a delivery and trips both merge gates. This was written down after a reviewed one-line hook fix was committed straight to main on 2026-08-24 — the change was sound and the route was wrong, which is exactly the case prose has to catch, because no gate does.
- **Every karta binder is reviewed before commit — always.** Same for landing a delivery branch on main. The stakes are the framework itself: a flawed binder propagates into every consumer repo. That requirement has not changed; what performs the review has.
- **Roundtable is back on, and it is the enforced review.** `.karta/roundtable.json` carries `enabled: true` (restored 2026-08-23), so both gates fire: a binder commit and an integration-branch merge each need a fresh record of that exact content, committed alongside it. Three steps: run the roundtable tool on the target; after **every** round pipe the result to `scripts/roundtable/run_review.py --round --target <slug> --kind binder` so the round is kept in `.karta/roundtable/<slug>.rounds.json`; on the final round pipe it to `scripts/roundtable/run_review.py --record --target <slug> --kind binder`. `.karta/roundtable.json` carries `ledger: true`, so the gate requires the ledger in the commit beside the record, with its last round having reviewed exactly the bytes being committed — a record without its rounds does not pass.
- **The multi-lens panel still runs, and is not a substitute.** `scripts/review/binder_review_panel.js` is the same model wearing six hats, so it can never satisfy the `min_providers` floor — but it opens the source and runs the commands, which the roundtable cannot. Use both where the numbers matter. See [AGENTS.md](AGENTS.md) — "Review before commit".
- **Landing a delivery branch on main is the user's call — ask before you merge.** Assembling the branch and running the floor are yours; deciding it ships is not. `scripts/hooks/roundtable_gate.py` now blocks the merge, and `KARTA_SKIP_ROUNDTABLE` does not bypass it — but the gate cannot tell an agent from a human, so **never set `KARTA_LANDING_APPROVED=1` yourself**. The human's landing command is `KARTA_LANDING_APPROVED=1 git merge --no-ff --no-edit karta/<slug>/integration` — `--no-edit` because the gate denies a merge that could open an editor after it. Say the branch is assembled, say the floor result, and ask. See [AGENTS.md](AGENTS.md) — "Two human approvals, and only one of them is enforced".
- **"karta status" means open the Karta Watch page, not print a summary.** The page is the status surface this repo built; a wall of terminal text is a downgrade of it. Serve it with `uv run --script skills/karta-status/scripts/serve_status.py --hub --port <port>` and hand over the keyed URL first. Check whether one is already listening before starting another — the session-start hook prints the live URL, and a second server on a second port is two pages disagreeing about which is current. Text is for what the page cannot show: an in-flight worker's progress, or a reading of something the page renders but does not interpret.
- **Never record a panel result as a roundtable.** Every lens is the same model wearing a different hat, so it cannot meet the `min_providers` floor. Do not pipe it to `scripts/roundtable/run_review.py --record`, and do not file it under `.karta/roundtable/`.
